## Context

Проект использует C++11, SFML 2.5.1, и имеет два варианта сборки: `make` (Makefile) и `cmake` (CMakeLists.txt). Текущий `CMakeLists.txt` собирает все исходники в один исполняемый файл `shooter`. Тесты требуют доступа к внутренним классам проекта, поэтому необходимо выделить исходный код в библиотеку.

## Goals / Non-Goals

**Goals:**

- Интегрировать Google Test через `FetchContent` для автоматического скачивания и сборки
- Выделить исходники проекта в статическую библиотеку `shooter_lib`
- Создать цель CMake `tests` для сборки и запуска тестов
- Обеспечить совместимость с существующим процессом сборки через `make`
- Покрыть тестами ключевые компоненты: `GameState`, `GameObjects`, `Fabric`, `EventHandler`

**Non-Goals:**

- Полный рефакторинг CMakeLists.txt (оставляем минимально инвазивные изменения)
- Интеграция с CI/CD (можно добавить позже отдельным изменением)
- Покрытие тестами всех классов сразу (начинаем с ключевых компонентов)
- Изменение процесса сборки через `make`

## Decisions

### 1. FetchContent вместо find_package или подмодуля

**Выбор**: CMake `FetchContent`

**Альтернативы рассмотрены**:

- `find_package(GTest)` — требует предустановки Google Test в систему, не работает на чистых машинах
- Git submodule — требует ручного `git submodule update`, сложнее в поддержке
- Скачивание архива вручную — не автоматизировано, сложно обновлять

**Обоснование**: `FetchContent` автоматически скачивает и собирает зависимость при первом запуске CMake. Не требует предустановки, работает кроссплатформенно, легко обновляется изменением версии в одном месте.

### 2. Статическая библиотека вместо объектной

**Выбор**: Статическая библиотека `shooter_lib`

**Альтернативы**:

- Объектная библиотека (OBJECT) — проще, но не генерирует архив, сложнее с линковкой
- Повторная компиляция исходников в тестах — дублирование, долгая сборка

**Обоснование**: Статическая библиотека компилируется один раз, линкуется и в основной executable, и в тесты. Уменьшает время сборки и обеспечивает единообразие.

### 3. Структура директории tests/

**Выбор**: `tests/` с поддиректориями по аналогии с `src/`

```
tests/
├── GameState_test.cpp
├── GameObjects_test.cpp
├── Fabric_test.cpp
├── EventHandler_test.cpp
└── CMakeLists.txt
```

**Альтернативы**:

- Все тесты в корне `tests/` — работает при малом количестве файлов, но усложняется при масштабировании
- Отдельная директория `test/` — просто другой конвеншн, не принципиально

**Обоснование**: Зеркалирование структуры `src/` упрощает навигацию и поддерживает конвенцию «тест рядом с кодом».

### 4. Минимальные изменения в существующем CMakeLists.txt

**Выбор**: Минимально инвазивные правки — выделение `shooter_lib`, добавление опций для тестов

**Альтернативы**:

- Полная переработка CMakeLists.txt сmodern CMake practices — рискованно для существующего проекта
- Отдельный CMakeLists.txt для тестов — невозможно, так как тесты зависят от исходников проекта

**Обоснование**: Минимальные изменения снижают риск поломки существующей сборки и упрощают ревью.

## Risks / Trade-offs

**[Risk] Скачивание Google Test при первом запуске CMake может быть медленным** → Митигация: указать конкретную версию (рилиз), использовать `FetchContent_Declare` с `DOWNLOAD_EXTRACT_TIMESTAMP`. При повторных запусках CMake использует кэш.

**[Risk] Изменение CMakeLists.txt может сломать существующую сборку через make** → Митигация: Makefile не затрагивается; CMakeLists.txt изменяется минимально. Проверка: `make && ./run` продолжает работать.

**[Risk] Тесты могут требоватьSFML- зависимостей (окно, рендеринг)** → Митигация: тестировать только логику, не затрагивая рендеринг. Использовать моки или изолировать тесты отSFML-вызовов.

**[Trade-off] Google Test скачивается при сборке, а не поставляется с проектом** → Это chấpлемо для open-source проекта; для Offline-сборки можно добавить опцию USE_SYSTEM_GTEST позже.
