## Context

`LevelGenerator::generateTrees` (`src/LevelGenerator.cpp`) chooses every third wide ground block and grows a tree. Previously the trunk height was random (100–200) and the clearance to the ground block overhead was ignored, so trees collided with platforms. See `proposal.md — Why`.

Constraints:
- C++11, `make` + CMake, tests with GoogleTest.
- Cyclomatic complexity budget: helpers keep to a single loop / single branch.
- TDD; keep the TMX tree path (`src/Map.cpp`) working.

Measurements on real generated levels (500 seeds, seeded after `LevelGenerator` construction, which itself calls `srand(time(0))`):
- 67% of tree spots have a ground block within 500px overhead; 35% have 2–3 stacked.
- Only 60% of blocks have any clear 500px trunk column; 40% are blocked across their whole width.

This ruled out "raise the interfering block": for 35% it means shifting a stack of wide blocks, which collides with neighbours and can push blocks off the top of the level, and it would break the existing reachability guarantees. Chosen approach: never move blocks; pick a clear trunk column or skip the block.

## Goals / Non-Goals

**Goals:**
- Trees are always 500px tall.
- Trees are climbable via evenly spaced step branches.
- Trees never intersect ground blocks overhead; ground blocks never move, so level reachability is untouched.

**Non-Goals:**
- Moving or re-generating platforms.
- Guaranteeing a tree on every eligible block (blocked blocks are skipped).
- Changing the TMX tree path or the legacy single-branch-per-side tree mode.

## Decisions

### Decision 1: Fixed height 500px
`TREE_HEIGHT = 500`, `TREE_TRUNK_HEIGHT = 2 * TREE_HEIGHT / 3 = 333`. `Tree` computes `leavesHeight = trunkHeight / 2 = 166`, so the total is 499px (within the 2px rounding tolerance). Keeping the existing `Tree` leaf formula avoids touching the trunk/leaves geometry requirements.

### Decision 2: Step branches via a new `branchStep` parameter
`TREE_BRANCH_STEP = 90` (< 110 jump limit). The 6-argument `Tree` constructor keeps the legacy random branches (TMX compatibility); a new 7-argument overload takes `branchStep`. When `branchStep > 0`, `generateLadderBranches` places a branch every `branchStep` px from the base to the top of the tree, alternating sides, each base inside the trunk x-range. `Fabric::createTree` gets a matching overload; `LevelGenerator` passes the step.

- Alternative: always ladder. Rejected because `src/Map.cpp` relies on the old behaviour.

### Decision 3: Clear-column placement, never move blocks
`clearTrunkPositions` scans `x` from `block.x + 100` to `block.x + width - 100` in 25px steps and keeps positions where `clearanceAtX(x) >= TREE_HEIGHT`. `clearanceAtX` is the minimum clearance over ground blocks that overlap `[x, x + TRUNK_WIDTH]` above the block. `buildTree` picks a random clear position, or skips the block when none exists.

- Alternative: raise the overhead block(s). Rejected (see Context).
- Alternative: reserve tree columns during platform generation. Rejected as a much larger rework with reachability risk; not needed because 60% of blocks already have a clear column and skipping the rest keeps the change small.

### Decision 4: Helpers keep complexity ≤ 2
`blocksOverhead` (one expression), `clearanceAtX` (one loop, one branch), `clearTrunkPositions` (one loop, one branch), `isTreeCandidate` (one expression), `buildTree` (one branch), `generateTrees` (one loop, one branch).

## Risks / Trade-offs

- [Fewer trees: ~40% of eligible blocks are skipped] → Acceptable; ~2 trees per level remain, and no platform is disturbed. Matches the user's chosen trade-off.
- [Branch ladder horizontal reach between sides] → Branches start inside the trunk x-range, so the player climbs by jumping straight up at the trunk; side alternation does not create a horizontal gap at the trunk.
- [Integer rounding makes the tree 499px instead of 500] → Within the documented 2px tolerance; leaves stay `trunkHeight / 2`.

## Revision: bottom-up per-column generation with reserved tree room

The clear-column/skip approach produced too few trees: 40% of eligible blocks had no clear 500px column, and platforms were still generated by horizontal levels. The generator was rewritten bottom-up.

### Decision 5: One upward neighbour per block, chosen per column
`generatePlatforms` starts from the fixed start block and grows a frontier. Each block places exactly one neighbour above it with a random horizontal gap in `[MIN_BLOCK_GAP, MAX_HORIZONTAL_REACH]` and a vertical step of 50–100px. Levels are no longer horizontal. Placement still uses `SpacingGrid` for the 100px clearance.

### Decision 6: Tree-carrying blocks reserve a full TREE_HEIGHT
`isTreeCandidate(block, index)` (every third block wide enough) is evaluated during generation using the ground-block index. For such a block the upward neighbour is placed `TREE_HEIGHT = 400` above instead of 50–100, reserving room for the tree. `LeavesGeometry`/trunk ratio is unchanged, so the tree is 399px tall (within tolerance). `TREE_BRANCH_STEP = 90` keeps every branch step within the 110px jump limit and the top branch within reach of the reserved block.

### Decision 7: Branches count as platforms for reachability
Because a tree-carrying block's neighbour is a tree-height away, ground-block-only reachability no longer holds there. The tree's ladder branches bridge the gap. The reachability requirements and tests were updated: an upward neighbour is reachable if it is within `MAX_JUMP_HEIGHT`, or within `TREE_HEIGHT` when the lower block carries a tree (the branches provide the path). `generateTrees` now places a tree on every candidate because the room is guaranteed.

### Consequences
- `PlatformVerticalSpacingDoesNotExceedMaxJumpHeight` allows gaps up to `TREE_HEIGHT` (tree-bridged).
- `RealGeneratorGivesEveryBlockAReachableUpwardNeighbor`, `...UpwardNeighborGapIsWithinReach` and `...HasClimbablePathFromStartBlock` take tree bridging into account.
- New test `RealGeneratorReservesRoomForEveryTreeCandidate` asserts every candidate gets a tree.
